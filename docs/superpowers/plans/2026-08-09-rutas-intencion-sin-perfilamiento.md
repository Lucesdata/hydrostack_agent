# Rutas de intención sin perfilamiento — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add an intent-based routing block to the home page (3 action cards, no profile selector), ship a lightweight `/soluciones` landing page for the "community" audience, and passively capture behavioral intent signals for authenticated users — all additive, zero changes to existing routes' behavior.

**Architecture:** Pure Next.js App Router additions. The home page (`app/page.js`) gets one new section reusing its existing `.bp-pillars-wrap` / `.bp-pillars-grid` / `.bp-card` CSS (already responsive, already visually correct) — no new CSS classes, no changes to the scroll-driven `useBlueprintFX` hook. `/soluciones` is a new server component styled with an inline `<style>` block following the `clr-*` prefix convention already used by `app/mis-coincidencias/page.tsx`. Signal capture is a new Drizzle table in the existing Neon DB (not Supabase Postgres — see Task 3 note on RLS), written through a single small helper called from three existing/new server-side call sites.

**Tech Stack:** Next.js 14.2.3 App Router, React 18, Drizzle ORM (Neon Postgres), Supabase Auth (`getSessionUser`), Vitest.

---

## Important deviation from the spec — read before Task 3

The spec asks for a `user_signals` table "with RLS (each user reads/writes only their own)". This repo's Postgres is **Neon**, reached through a single shared `DATABASE_URL` via Drizzle — never through Supabase's own Postgres/PostgREST layer with a per-user JWT. `CLAUDE.md` §4 documents this explicitly: *"No hay RLS en Postgres — la única defensa multi-tenant es el `WHERE usuarioId=...` de cada query de aplicación."* Postgres RLS policies keyed on `auth.uid()` would never fire through this connection — there is no precedent anywhere in the codebase for impersonating the end user at the DB layer, and adding one here would be a new, inconsistent pattern.

Task 3 below therefore implements `user_signals` as a plain Drizzle table (same pattern as `oferente_perfil` / `envio_log` in `src/lib/db/schema/cuentas.ts`), enforced the way every other multi-tenant table in this app is enforced: every read/write scoped by `usuarioId` in application code, never trusting a client-supplied id. This is not a scope reduction — it's using the isolation mechanism this app actually has. Flag to the user if this substitution isn't acceptable.

/**
 * Señal pasiva de intención (Prompt 02 — rutas sin perfilamiento). Ningún
 * flujo de UI pregunta el perfil del usuario; en su lugar registramos qué
 * acción tomó y de ahí se infiere. Sin RLS de Postgres — este DB (Neon) se
 * consulta siempre con el mismo DATABASE_URL de servidor, nunca como el
 * usuario final, así que una policy sobre auth.uid() nunca aplicaría (ver
 * CLAUDE.md §4). El aislamiento es el mismo de siempre en este repo: cada
 * query se filtra por usuarioId en código de aplicación.
 */
export const userSignal = pgTable(
  'user_signals',
  {
    id: uuid('id').defaultRandom().primaryKey(),
    usuarioId: text('user_id')
      .notNull()
      .references(() => usuario.id, { onDelete: 'cascade' }),
    signal: text('signal').notNull(),
    creadoEn: timestamp('created_at', { withTimezone: true }).defaultNow().notNull(),
  },
  (t) => [index('user_signals_usuario_idx').on(t.usuarioId)],
);
```

// src/lib/signals/record-signal.ts

/**
 * Captura pasiva de intención (Prompt 02). Nunca debe romper el flujo que la
 * dispara — un fallo de insert aquí no es motivo para fallar una página o un
 * endpoint, así que se traga el error como getSessionUser() ya hace en
 * src/lib/supabase/get-session-user.ts.
 */

import { db } from '@/src/lib/db/client';
import { userSignal } from '@/src/lib/db/schema/cuentas';

export type UserSignal = 'oferente' | 'estructurador' | 'comunidad';

export async function recordUserSignal(usuarioId: string, signal: UserSignal): Promise<void> {
  try {
    await db.insert(userSignal).values({ usuarioId, signal });
  } catch {
    // Captura silenciosa — ver docstring del módulo.
  }
}
```
